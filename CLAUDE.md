# PDFX — PDF reader and annotator for Windows

A polished, native-feeling Windows PDF reader and annotator. Owner: Emil (communicates in Norwegian — respond in Norwegian). Product spec: `docs/SPEC.md`. Phased plan + architecture decisions: `docs/ROADMAP.md`. **Platform tiers + parity contract: `docs/PLATFORMS.md`** — Windows x64 is the reference; win-arm64/macOS/Linux and the extension are held to it, and any cross-platform divergence must be listed there. **Product copy: `docs/MESSAGING.md`** — the master for every user-facing claim; the README, `docs/index.html`, `docs/STORE-LISTING-DESKTOP.md` and `docs/STORE-LISTING.md` are renderings of it. Change a claim there first, never in one listing alone. **Release checklist: `docs/RELEASE.md`** — follow it for any release or large push. **Agent rig: `docs/AGENTS.md`** — the three Claude agents that run from GitHub Actions (weekly model review, issue triage, `@claude` on request): what each may do alone, what comes through Emil, and what none of them may ever do. Read it before adding a scheduled or event-driven agent. **AI test strategy: `docs/AI-TESTING.md`** — the four layers (mocked shaping, replayed real streams, live conformance with keys, real UI), what each one can and cannot catch, and what none of them covers. Read it before adding an AI test. **Monthly staleness audit: `docs/MAINTENANCE.md`** — the checklist behind the mid-month reminder issue (model catalogue, provider params, tokens, advisories). **Typography: `docs/TYPOGRAPHY.md`** — the three font roles (`--font-ui` / `--font-reading` / `--font-mono`), 600 as the one emphasis weight, italic in the reading role only, and the optional reading font chosen by name from the fonts the machine has (nothing shipped). Read it before touching a `font-family` or `font-weight`. CI (`.github/workflows/ci.yml`) builds all three OSes on every push.

**What ships is Emil's call.** Before a release or a big push, run `npm run check:shots`, then `npm run shoot` (keyless, English, every shot) and ask him which frames to ship — `shoot` writes to the gitignored `docs/screenshots/_auto/` and cannot overwrite the shipped set without `--out`. Cover shots must show the paper's title, authors and abstract, never the arXiv reproduction notice.

## Commands
- `npm run dev` — full Electron app with HMR
- `npm run dev:web` — renderer only in a plain browser on port 5199 (for UI preview/automation; Electron APIs are shimmed via `src/renderer/src/bridge.ts`)
- `npm run build:ext` / `npm run dev:ext` — build the browser-extension target to `dist-extension/` (a third `PdfxApi` platform alongside Electron; see `docs/BROWSER-EXTENSION.md`). Load unpacked in `edge://extensions`. `ext:local` builds and mirrors the result into the MAIN working tree's `dist-extension/` — the fixed path the browser has loaded (an unpacked extension's ID, and with it its whole `chrome.storage.local`, is derived from that path), which is what keeps a worktree build from leaving the sideloaded install stale; it also runs itself as `postbuild:ext` after every local build, silent on CI and on non-master branches. `ext:release [tag]` mirrors a published GitHub release's extension zip into the same folder instead — releases are built in CI and never touch it on their own, so RELEASE.md step 3 runs this after publishing. `pack:ext` zips it for Load-unpacked, `pack:ext:store` for store upload (manifest at zip root); `test:ext-publish` dry-runs the Edge/Chrome publish APIs (`docs/STORE.md`)
- `npm run typecheck` — tsc for all three targets: renderer (`config/tsconfig.web.json`), main/preload (`config/tsconfig.node.json`) and the extension (`config/tsconfig.extension.json`)
- `npm run build` — electron-vite production build to `out/`
- `npm run sample` — regenerate `src/renderer/public/sample.pdf` (test document)

## Architecture
- **electron-vite** layout: `src/main` (Electron main), `src/preload` (contextBridge → `window.api`), `src/renderer` (React 19 + TS), `src/shared/types.ts` (types shared across all three; `PdfxApi` is the single IPC surface).
- **pdf.js (pdfjs-dist v6) renders; it never writes.** **EmbedPDF (@embedpdf/pdfium + @embedpdf/engines, MIT/BSD-3) writes annotations** (standard annots + appearance streams; full-rewrite save behind a debounced document cache, `src/main/doc-cache.ts`) via `src/main/annotation-engine-embedpdf.ts` in the main process; annotations are drawn by our own React overlay, NOT pdf.js's editor layer. mupdf (AGPL) is a devDependency used ONLY as an independent verifier in `npm run test:engine` / `bench:engine` — never import it from `src/`. The app is MIT-licensed; keep every runtime dependency permissive. See docs/ROADMAP.md for rationale.
- **Text in images on pages with text of their own** (`src/renderer/src/ocr-image.ts`, driven by ocr.ts): a figure, a screenshot, a table pasted in as a picture. The pixels are the ones pdf.js already decoded (`page.objs`, found through `image-regions.ts`, which now records each image's object id and whether it is drawn upright) — nothing is drawn again on the main thread. The words join AFTER the page's own text (`mergeImageText`), so every offset into the own text is unchanged; PdfPage rebuilds the layer with them and marks those spans `data-ocr="image"`, and `matchSpans` in search.ts accepts a layer and a text that differ by the images' words alone (`ocrRunsFrom`). Only SEARCH waits for image words (`images: 'wait'`, with hits shown meanwhile); the assistant, the export and the markup take what is already read (`'available'`) and never start a reading — the assistant waits for scanned pages only (`useOcrProgress(pdf, true)`). A hit among image words waits for them to land in the layer (`inImageWords`). Finding a page's images asks for its operator list one page at a time, the pages on screen first.
- **Scanned pages get their text from OCR, on this machine** (`src/renderer/src/ocr.ts`): a page whose PDF has no visible text is rendered at 300 dpi (print intent — a display render waits on requestAnimationFrame and stops in a minimised window) and read by Tesseract (tesseract.js-core, Apache-2.0, wasm, in its own worker; models from `@tesseract.js-data`, by UI language: nb → nor+eng, en → eng+nor, zh → chi_sim+eng). Its words come back as pdf.js text content through `pageTextContent` in `search.ts` — the ONE source for both the text layer (PdfPage) and every PageText — so search, selection, text markup, annotation export and the assistant read a scanned page with no OCR branch of their own, and the spans↔runs invariant holds. Up to TWO engines read in parallel (measured 1.9× on the 30-page JSTOR scan; a third added 5 %), the second started only when a second page waits. Pages on screen jump the queue; a whole-document pass (search, the assistant) reports progress (`useOcrProgress`). `settings.ocrAuto` off = nothing is read until the reader asks for the document (`enableOcr` — the toolbar chip, the search bar note and the assistant's no-text notice offer «Gjenkjenn tekst»). The words live per pdf.js document, are carried across the swap every write makes (`carryOcr`) and are kept between sessions in IndexedDB (`ocr-store.ts`, 150 documents, keyed by /ID[0] + models) — never for a password-protected document (`allowOcrStore` is the opt-in each opener calls); nothing is written into the file. The wasm and the models are fetched by XHR in the renderer and handed to the worker (file:// refuses fetch), and the engine stops after a minute idle.
- Renderer works in a plain browser: `bridge.ts` falls back to fetch/localStorage/file-input when `window.api` is missing. Keep new platform calls going through `PdfxApi` so this stays true.
- App state (recents, per-file reading positions, theme, window bounds) is a hand-rolled JSON store in `userData/pdfx-state.json` (`src/main/storage.ts`).
- Themes = CSS variables on `<html data-theme="day|sepia|night|nightHc">` in `src/renderer/src/styles/app.css` (`nightHc` is Night+, the high-contrast dark mode; `auto` resolves to one of the four); page recoloring is a CSS `filter` on the page canvas (`--page-filter`, also applied to the annotation-marks overlay and live draw layer) plus `mix-blend-mode: var(--page-blend)` — sepia multiplies the canvas against the cream `--page-bg` so white paper takes the exact cream tone without washing out figure colours.
- Viewer (`PdfViewer.tsx`): pages absolutely positioned from a computed layout (tops array); visibility range computed mathematically on scroll (no IntersectionObserver); only pages within 800px of the viewport mount a canvas + text layer.

## Gotchas (hard-won)
- **pdfjs-dist v6 API**: `page.render({ canvas, viewport })` — pass the canvas, not `canvasContext`. Worker must be loaded via Vite's `?worker` import assigned to `GlobalWorkerOptions.workerPort` (a bare `?url` workerSrc hangs in dev).
- **pdf.js renders via requestAnimationFrame** → in a *hidden* tab (automated preview) rendering stalls and scroll events don't fire. `main.tsx` has a dev-only rAF→setTimeout shim; when driving the preview programmatically, dispatch `new Event('scroll')` manually after setting `scrollTop`. **CSS transitions also freeze at their start value in hidden tabs** — getComputedStyle will forever report pre-transition values even though the rule matches; to verify layout logic, inject `* { transition: none !important }` first. These are preview-environment artifacts, not app bugs.
- **Column-flex children have `min-height: auto`**, which beats `max-height: 0` — collapsing a bar (e.g. `.tab-bar`) needs an explicit `min-height: 0`.
- **Version pins**: electron-vite 5 requires vite ≤7 (vite 8 is out — do not upgrade blindly). pdf.js ships monthly majors — upgrade deliberately, `render`/TextLayer APIs churn. **Electron 43.1.0 and 43.1.1 cannot print on Windows at all**: a silent `webContents.print()` fails `Invalid printer settings` whatever printer is named, and the dialog form (what the app calls) never calls back at all until teardown, when it reports `false` with an empty reason — so Print does nothing and cannot even say so (issue #22, measured 2026-09-21 on one Windows box: 43.1.0 ✗, 43.1.1 ✗, 43.2.0 ✓, 43.7.3 ✓, 38.8.6 ✓). The lockfile had sat on 43.1.0 since the first commit while `^43.1.0` allowed six patches past it. A patch release is not cosmetic here — the floor in package.json is what keeps a fresh `npm install` off a broken one.
- pdf.js transfers the `data` buffer to its worker — always pass a copy (`payload.data.slice()`).
- Drag-drop needs `webUtils.getPathForFile` in preload to recover the real path (`File.path` is gone in modern Electron).
- **Full-page overlay hosts inside `.pdf-page` MUST be `pointer-events: none`** (only their interactive children `auto`) — otherwise they silently kill text selection. This bit us with the link layer.
- **`touch-action` cannot tell a pen from a finger** (both are direct-manipulation pointers on Windows — a pen drag PANS a scrollable area unless touch-action forbids it). The draw layer therefore allows finger panning by default and flips to `none` via `html.pen-near`, set from pen HOVER events (Windows pens report from ~5–10 mm out, so the flip lands before contact — this is also the palm guard). Consequences: synthetic/CDP pen input must hover before pressing or the browser pan wins and CANCELS the pointer; and `pointercancel` on the draw layer must DISCARD the in-progress stroke, never commit it (a committed stub under the pan the user actually asked for).
- **`mix-blend-mode` dies silently inside ANY stacking context** (per CSS compositing, every stacking context is an isolated group — `z-index` on a positioned ancestor is enough): the child then blends against the ancestor's transparent background, degrading to a plain alpha wash. This shipped broken for a while (highlights greyed the text) and survived several "fixes" because `getComputedStyle` still reports the blend mode — the ONLY valid proof is composited pixels (an SVG `foreignObject` fixture drawn to a canvas works in-page). Blend hosts inside `.page-raster` need `z-index: auto`; to blend a whole layer that must keep its z-index (e.g. `.draw-layer`), put the blend on the stacking-context element itself. Inline `<svg>` children never blend with HTML behind them — the blend goes on the `<svg>` element.
- **Zoom commits must anchor an exact page point** (pageIndex + in-page coords), not multiply scroll by the ratio — gaps/margins don't scale with zoom, and the transform must be removed in the same `useLayoutEffect` that sets the new scroll or pinch-release visibly jumps. Owner cares a lot about this being seamless.
- Search maps text offsets → screen via the text-layer spans; spans correspond 1:1 to `getTextContent()` items with `str !== ''` (in order). If that invariant breaks (e.g. `includeMarkedContent` gets enabled), `resolveMatchRects` returns null.
- **A FreeText can only carry the 14 standard PDF fonts.** PDFium builds its appearance stream from its own copies of those, and `FPDFAnnot_AppendObject` — the only way to put a real embedded-font text object into an annotation — refuses every subtype except STAMP and INK. So "add a nicer font to the text tool" is not a small change: it means leaving FreeText behind for a Stamp full of drawn glyph outlines, with re-baking on every move/resize/edit and no extractable text in the file. v0.36 did exactly that for a handwriting font and it was removed in v0.37. The text tool's typeface menu (`TEXT_FONT_FAMILIES` in `annotations.ts`) is Helvetica/Times/Courier × bold/italic and stops there on purpose.
- **EmbedPDF `getPageAnnotations` makes PDFium synthesize `/AP` for border-only Link annots** (hyperref's `/Border[0 0 1]/C[0 1 0]` — the green/red citation boxes arXiv PDFs define but no modern viewer draws). pdf.js only skips those boxes BECAUSE the appearance is missing, so a save after that call bakes them visible everywhere. Both engines bracket every op with `src/shared/link-ap-guard.ts` (snapshot AP-less links → strip exactly those after); keep the guard around any NEW engine call that loads page annotations. Regression-tested in `test:engine` ("linkguard").
- The dev preview panel may attach multiple browser contexts to the same URL: console logs appear N times and `preview_click`/`preview_eval` can hit different contexts — do click + assert inside a single `preview_eval`.
- **`webContents.startDrag` blocks main until the OS drop ends — and with NO mouse button held it never ends.** The Windows drag loop (DoDragDrop) waits for the release of the button that was down when it started; called from a synthetic dragstart, a touch or pen drag, or any code path with no button down, it wedges the whole main process (no IPC, no DevTools, Task Manager only — measured 2026-09-17 against the built app). Electron has no API for the button state, so the only guard is the caller's: `TabBar.tsx` records the pointerdown before a drag and starts the native drag ONLY for `pointerType === 'mouse'` with the left button down (and no Ctrl/Cmd — Ctrl+drag, Cmd on macOS, is the in-app move); everything else keeps the HTML5 drag and `tab:drop-at-cursor`. The modifier cannot be Shift: Chromium starts NO drag from a Shift+mousedown on anything but a link or image (Shift+press extends the selection), so a Shift-drag fires neither dragstart nor dragend — it silently does nothing (2026-09-17). Gate on the POINTERDOWN record, never on `DragEvent.buttons` — Chromium reports 0 there, and that check silently sent every real mouse drag down the fallback (it pasted the path as text into the target AND tore off a new window). Never call `startDrag` from a path that cannot prove a held mouse button. `test:tab-drag` guards the gate.
- **`npm run dist` / `dist:store` fails with `EPERM: rename win-unpacked.tmp -> win-unpacked`** when a stale unpacked dir exists at build start: electron-builder deletes it, but Windows defers the delete while Defender holds a handle, so the rename hits a delete-pending directory. Fix: `Remove-Item -Recurse -Force release/win-unpacked*, release/win-arm64-unpacked*` before building — the arm64 pass has its own directory and fails the same way half-way through an otherwise successful build. Retrying without cleaning just fails again.
- **The installer's size lives in `dependencies`, not in `files`.** electron-builder collects production `dependencies` on a separate path that the `files` list does not constrain, so a renderer-only package listed there ships a second copy on top of the one vite already bundled. Renderer imports belong in devDependencies (react, pdfjs-dist, katex …); only what main/preload `require` at runtime goes in `dependencies`. `@embedpdf/engines` drags in 150 MB of font packs it resolves from a CDN anyway — excluded in `config/electron-builder.yml`.

## Conventions
- UI strings in Norwegian bokmål. Code, comments, commit messages in English. Three dictionaries: `nb` is the master in `src/renderer/src/i18n.ts`, `en` beside it, `zh` (Simplified Chinese, issue #32 — machine-translated by Claude, native-speaker PRs welcome) in `src/renderer/src/i18n-zh.ts`; `Dict` is `nb`'s key set, so a new string without its English AND Chinese lines fails typecheck — write all three in the same change. The AI prompts have Norwegian and English texts only; a Chinese interface gets the English prompt with the answer language named (`answerLanguage`/`uiLanguageNote` in `ai.ts`). main's native dialogs carry their own three strings (`dialogLanguage` in `src/main/index.ts`).
- No new dependencies without checking the maintained/ESM story; prefer hand-rolling small things (see storage.ts).
- Design language: calm, muted chrome, accent `--accent` blue, generous whitespace; every visual choice should hold up under close side-by-side scrutiny.
